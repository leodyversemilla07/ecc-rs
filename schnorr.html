Schnorr signatures

BIP-340 Schnorr signatures, the scheme Bitcoin's Taproot uses. Where ECDSA hides a nonce inside a pair of numbers, Schnorr keeps everything in one line: s·G = R + e·P. This page walks through signing and verification, using the same rules the crate uses.

the formulasBIP-340, stage by stage

The whole scheme, in one place. Everything here is what schnorr/src/lib.rs computes — the trace below replays it with your own numbers.

1 · public key

P = d·G·pk = x(P)

public_key — only the x-coordinate is published. BIP-340 fixes the y implicitly to the even one, which is what makes 32 bytes unambiguous.

2 · the nonce

t = bytes(d) ⊕ hashaux(a)
rand = hashnonce(t ‖ bytes(P) ‖ m)

The nonce is derived, not random. Hashing the secret key into it means a broken RNG cannot leak the key — and the auxiliary randomness a is what stops the same message signing to the same nonce twice.

3 · the challenge

e = int(hashchallenge(bytes(R) ‖ bytes(P) ‖ m)) mod n

The challenge commits to the public key, the nonce point and the message. That is what makes Schnorr non-malleable — ECDSA does not put the public key into its hash.

4 · signing

R = k·G·s = (k + e·d) mod n

sign_once — the signature is r = x(R) and s. Note there is no modular inverse anywhere: ECDSA needs k⁻¹, Schnorr does not.

5 · verifying

R′ = s·G − e·P·valid ⇔ has_even_y(R′) ∧ x(R′) = r

verify — the verifier rebuilds R′ from public data only and checks the x-coordinate and the even-y convention. The secret key never appears.

the equation it all rests on

s·G = (k + e·d)·G = k·G + e·(d·G) = R + e·P

One line, and it is additive. That single property is why Schnorr is provably secure, why (r, n−s) does not verify, and why several signers can produce one signature together (MuSig, threshold signatures).

Each hash uses its own tag — BIP0340/aux, BIP0340/nonce, BIP0340/challenge — so the three hashes cannot be confused with one another or with any other hash.
the signature64 bytes, always

public key — 32 bytes

Only the x-coordinate of the public point is published. The y-coordinate is implied: of the two points with that x, BIP-340 always means the one with the even y. That is what lift_x recovers during verification.

signature — 64 bytes

r is the x-coordinate of the nonce point R, and s is the scalar. Together they satisfy s·G = R + e·P.

why verification worksthe algebra

Signing produces s = k + e·d and R = k·G. Multiplying the first by the generator:

s·G = (k + e·d)·G = k·G + e·(d·G) = R + e·P

The verifier knows R (it is in the signature), P (the public key) and e (a hash of the message), so it can rebuild the right-hand side and check that the x-coordinate matches. The secret key never appears — and because the equation is additive, several signers can produce one signature together, which is what MuSig and threshold signatures do.

notes

the nonce is derived, not random

BIP-340 derives the nonce from the secret key and the message with a tagged hash. That removes the need for an RNG at signing time, but it also means the derivation must never repeat — which is why the auxiliary randomness exists.

tagged hashes

Every hash is prefixed with SHA256(tag) ‖ SHA256(tag), so a hash used for the nonce cannot be replayed as the challenge, and a hash from another scheme cannot be reused here.

the even-y convention

Signing negates the secret key when the public point has an odd y-coordinate, and the nonce when R does. Everything published therefore has an even y, and lift_x can reconstruct the point unambiguously.

the nonce must never repeat

Reusing a nonce gives away the private key. Because the nonce is derived from the secret key, BIP-340 mixes in auxiliary randomness and hashes the public key into the derivation, so a mistake in one signature cannot leak the key for another.
